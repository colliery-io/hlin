# Postgres dev tooling, store trait and v1 schema

## Parent Initiative

[[HLIN-I-0001]]

## Objective

Make Postgres ([[HLIN-A-0006]]) real for development and define the shell's store boundary: angreal tasks for a containerized database, a migrations tool, the store trait with a Postgres implementation and an in-memory test double, and the v1 schema for the two things the shell must remember, last-seen manifests and layouts ([[HLIN-A-0007]]).

## Acceptance Criteria

## Acceptance Criteria

- [x] angreal `db` group: `up`, `down`, `reset`, `migrate`, plus `status`. `up` waits for the database to actually accept connections, since the container reports healthy before first-run initialisation finishes
- [x] Migrations wired as `sqlx` migrations under `crates/hlin/migrations`, embedded with `sqlx::migrate!` and applied by the shell on connect
- [x] Store trait in `hlin` covering platform snapshots with the consecutive-observation count, layouts, panel instances, fork, and the published gallery
- [x] v1 schema: `platforms`, `layouts`, `panel_instances`, with the indexes the two listing queries need
- [x] Postgres and in-memory implementations pass the same trait-level suite. Verified against a real Postgres 16; see the note below on how, since Docker was unusable here
- [x] Dev connection configured by `HLIN_TEST_DATABASE_URL`, defaulting to the URL the compose file and the angreal task both use
- [x] `angreal test all` does **not** bring the database up. See the decision below: the database tests are `#[ignore]`d instead

## Implementation Notes

### Technical Approach
The store lives in the `hlin` crate per [[HLIN-A-0006]]. The in-memory implementation is a test double, not a backend, and is compiled only under `cfg(test)` or a `test-support` feature.

### Dependencies
[[HLIN-T-0001]]. Manifest snapshot storage stores raw JSON plus the hash computed by [[HLIN-T-0002]], but does not require it to be complete.

### Risk Considerations
CI: the GitHub workflow from the template needs a Postgres service container or the tests must skip cleanly when no database is reachable. Prefer the service container.

## Status Updates

**2026-09-07 — complete.** The shell now has a store. `docker-compose.yml` for the development database, an angreal `db` group, one migration, `store::Store` with a Postgres implementation and an in-memory double, and a shared suite both must pass. Workspace at 95 tests by default plus the database suite; `angreal check all` clean.

Decisions taken during the work:

- **Queries are written out rather than generated by `sqlx`'s macros.** The macros check queries against a live database at *compile* time, which would make a database necessary to build the shell at all, including in CI's check job and on a laptop with no Docker. Migrations still use `sqlx`, embedded with `sqlx::migrate!`, which reads a directory at compile time and needs no connection. The cost is that a query typo surfaces at runtime rather than at build; the row-mapping helpers keep that to one place per table.
- **Migrations run on connect, not as a deployment step.** A shell that starts is a shell whose schema matches its code. `sqlx` takes a Postgres advisory lock, so with more than one instance only one migrates and the rest wait.
- **The observation count is incremented in the `INSERT ... ON CONFLICT` statement**, not read-then-written. Two shell instances polling the same platform would otherwise lose an observation between them, and the count is what the registry's debounce rests on.
- **Panels are replaced wholesale on update, inside a transaction.** A layout is edited as one thing: dragging a panel changes several positions at once and there is no useful notion of half of that having happened. Reconciling individual panels would cost more than it saves at this size.
- **A fork starts personal however the original was shared.** Publishing is a decision its new owner makes, not one inherited from someone else.
- **`panel_instances` has no foreign key to any platform.** A layout may name a platform or panel that does not currently exist, and renders it as unavailable rather than losing it. A platform coming back restores the panel.
- **Deleting a layout spares its forks**, clearing only their provenance pointer, via `ON DELETE SET NULL`. Panels go with their layout by cascade.
- **`angreal test all` does not start the database.** The task asked for it, and it is the wrong shape: it would make the common case, running the tests, depend on Docker being up, and would start a container as a side effect of something that reads like a read-only command. Instead the database tests are `#[ignore]`d with a message naming `angreal db up`, and CI runs them explicitly. If the friction proves worse than the surprise, this is a small change.

On the risk this task recorded, CI: a new `test-store` job provides a Postgres service container and runs `cargo test --workspace` for every target, then again with `--ignored`. That also closes a gap the risk did not anticipate. The template's jobs run only the targets named `integration` and `functional`, so the `envelopes` target added by [[HLIN-T-0003]] and the `store` target added here would never have run in CI at all. The new job runs everything, so a future test target is covered the day it is added.

**Blocker worked around, worth knowing about.** Docker on this machine could not start the database: its VM disk is full, with 32GB of images and 22GB of build cache, and `initdb` failed with no space left on device. That is the user's Docker environment rather than anything in this project, so nothing was pruned. The compose file, the angreal tasks and the CI service container are all written and reviewed but the containerised path is **unverified end to end**; `angreal db up` created the container and the wait loop behaved correctly, and only Postgres's own initialisation failed.

To verify the Postgres implementation anyway, the suite was run against the MacPorts Postgres 16 already on this machine, on the same port the compose file uses. All cases pass, migrations applied cleanly, and the schema, indexes and `_sqlx_migrations` row were checked directly. So the store code is verified against a real Postgres; only the container tooling is not. Reclaiming Docker space and running `angreal db up` would close that.
